# Стадия 3: BM25 и гибридный поиск

Добавлены три режима `search --mode dense|bm25|hybrid`. По умолчанию остаётся dense.
BM25 реализован явно на стандартной библиотеке Python. Новых зависимостей и
миграций нет. Сравнение использует прежний корпус и прежнюю разметку без изменений.

## Зачем второй поисковый сигнал

Dense search сравнивает представления смысла, но может спутать соседние темы.
Лексический поиск полезен для конкретных слов и названий. BM25 оценивает совпадения
термов с учётом их частоты, редкости и длины текста. Он не переводит запросы и
сам по себе не понимает синонимы.

Альтернативы: PostgreSQL full-text search, готовая BM25-библиотека, Lucene/OpenSearch
или sparse vectors в Qdrant. Для первого учебного baseline выбран собственный
инвертированный индекс: `терм → {chunk_id: частота}`. Так алгоритм можно прочитать,
проверить по ручному расчёту и объяснить без инфраструктурных деталей.

## Токенизация и BM25

Токенизатор версии `nfkc-casefold-unicode-alnum-v1` делает Unicode NFKC, casefold
и выделяет последовательности букв/цифр. Например, `KV_cache 4-bit` превращается
в `kv`, `cache`, `4`, `bit`. Русские буквы сохраняются, но не переводятся.
Нет стемминга, лемматизации, удаления стоп-слов или отдельного поля заголовка.
Повторяющиеся термы запроса учитываются один раз. Пунктуационный запрос и запрос
без совпадений возвращают пустой список; нулевые совпадения не заполняют top-k.

Здесь единица поиска — **чанк**, поэтому N и df считаются по чанкам:

```text
idf(t) = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))
score(q,d) = sum over unique query terms:
    idf(t) * tf(t,d) * (k1 + 1)
    / (tf(t,d) + k1 * (1 - b + b * length(d)/average_length))
```

`k1=1.2` управляет насыщением частоты: вклад повторений растёт с убывающей отдачей.
`b=0.75` управляет нормализацией длины; при `b=0` она отключена. Использован
положительный вариант IDF, также описанный в [Lucene BM25Similarity](https://lucene.apache.org/core/9_12_1/core/org/apache/lucene/search/similarities/BM25Similarity.html).
Общее объяснение — [Stanford IR book](https://nlp.stanford.edu/IR-book/pdf/11prob.pdf).
Это не побитовая копия Lucene: обработка полей, токенов и норм отличается.

BM25 строится при каждом запросе из текущих документов PostgreSQL. Фильтры применяются
до построения индекса; DF и средняя длина относятся к выбранному подкорпусу.
Изменение фильтра может поэтому изменить score. Совпавшие чанки сортируются по
убыванию score, при равенстве — по строковому UUID. Канонический текст и актуальность
повторно проверяются перед выдачей, поэтому результат может содержать меньше k чанков.

## Объединение через RRF

Для каждого чанка складываем `1 / (60 + rank)` из двух выдач, ранги начинаются с 1.
Отсутствие в ветке даёт нулевой вклад. Один chunk ID присутствует в итоговой выдаче
один раз. Равенство итогового score разрешается по UUID. Исходные значения BM25 и
cosine напрямую не складываются; итоговый RRF score не является вероятностью.
[Первоисточник RRF](https://cormack.uwaterloo.ca/cormacksigir09-rrf.pdf).

По умолчанию каждая ветка отдаёт до 20 кандидатов; после объединения возвращаем k.
`--candidate-k` изменяет эту глубину для hybrid, предел 100; она должна быть не меньше
k. В нашем корпусе всего 20 чанков: dense может передать весь корпус. Это существенно
облегчает задачу fusion и не моделирует усечение кандидатов большого индекса.

Простое сложение scores потребовало бы решения о нормализации и весах. RRF —
понятная стартовая альтернатива, но он теряет информацию о величине разрыва scores.
Плохая ветка может ухудшить итоговую выдачу. Настройки 20/60 и 1.2/0.75 выбраны до
замера, поиск лучших параметров на текущем наборе не проводился.

## Актуальность и доступность

Самостоятельный BM25 требует только PostgreSQL и ищет все текущие документы,
даже если они не имеют векторов. Он не загружает E5 и не обращается к Qdrant.
`--collection-prefix` и `--approximate` для этого режима отклоняются.

В hybrid обе ветки допускают только `current + ready` выбранной коллекции.
После RRF проверка выполняется снова. Поэтому незавершённая индексация не возвращается
через лексическую ветку в обход правил dense. При сбое Qdrant hybrid завершается
ошибкой; скрытого переключения на BM25 нет. Ветки последовательные; общей транзакции
между ними нет. Проверка защищает от устаревшей выдачи, но не гарантирует единый
снимок всех рангов при конкурентных обновлениях.

## Запуск

BM25 после обычного ingestion не требует optional model dependencies:

```bash
export RAG_DATABASE_URL='postgresql+psycopg://rag:rag_local@127.0.0.1:55432/rag'
uv run --locked agentic-rag search "low rank adapters" --mode bm25 --k 5
```

Если extra embeddings уже установлен, используйте `--extra embeddings` в uv-командах,
чтобы uv не удалил его при синхронизации окружения. Для hybrid и сравнения:

```bash
uv sync --locked --extra embeddings
docker compose up -d postgres qdrant
uv run --locked --extra embeddings agentic-rag db-upgrade
uv run --locked --extra embeddings agentic-rag evaluate benchmarks/dense_v1/dataset.json \
  --compare --collection-prefix rag_dense_v1 --output artifacts/comparison.json
uv run --locked --extra embeddings agentic-rag search "KV cache memory blocks" \
  --mode hybrid --collection-prefix rag_dense_v1 --candidate-k 20 --k 5
```

`evaluate --compare` загружает модель один раз, обеспечивает индексацию набора и
последовательно измеряет dense, BM25, hybrid. Для сопоставимости все три режима
оценки ограничены одними `current + ready` документами; это отличается от свободного
BM25 CLI, которому готовность векторов не нужна. Команда записывает/активирует
документы набора в БД. Она не изменяет corpus/qrels. Сохраняйте повторные отчёты в
`artifacts/`, чтобы не перезаписывать первые измерения.

В отчёте есть параметры, qrels, ранги, scores, метрики @1/3/5 по каждому вопросу и
языку, время запроса. BM25-время включает чтение корпуса и построение индекса;
model loading исключён. Это стоимость текущего workflow, а не сравнение скорости
чистых алгоритмов. Результаты: [results.md](results.md).

## Ограничения и рост

Вся коллекция выбранных чанков загружается в память на запрос. Есть инвертированный
индекс, но нет его долговременного хранения и обновления по изменениям документов.
На большом корпусе нужны переиспользуемый снимок индекса, пакетные обновления и
согласование его версии с PostgreSQL. Возможен переход к отдельному поисковому
движку после измерения масштаба; это не сделано заранее.

NFKC и разбиение идентификаторов могут потерять различия в техническом тексте.
Без лемматизации разные формы слов не совпадают. Без перевода шесть русских
вопросов текущего набора не имеют ни одного лексического совпадения. Стоп-слова
могут добавлять нерелевантные результаты. Overlap также влияет на DF и дублирование
доказательств. Эти ограничения требуют отдельной оценки, а не обещания универсального
улучшения от hybrid. Сам набор остаётся маленьким, составленным ассистентом,
без независимого test split и с неполной разметкой.

## Что нужно знать для интервью

1. TF — частота терма в чанке, DF — число чанков с термом; это разные величины.
2. BM25 ограничивает пользу повторений и учитывает длину текста.
3. Токенизация — часть контракта индекса и должна совпадать для запросов и корпуса.
4. RRF объединяет ранги и не требует общей шкалы исходных scores.
5. Глубина кандидатов ограничивает, что fusion вообще может найти.
6. Corpus statistics, фильтры и версия корпуса влияют на BM25 score.
7. Hybrid может улучшить MRR без изменения Recall, но улучшение не гарантируется.

Вопрос для разбора: почему в BM25 недостаточно учитывать только число повторений
слова в чанке — зачем нужен ещё IDF?
